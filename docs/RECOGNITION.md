# あいさつの練習判定

調査・更新日: 2026-10-18（日本時間）。

## こんにちはの判定修正・段階別画像（2026-10-18 追記）

現在の画面は「こんにちは」だけを公開する。以下の旧3教材の記録は履歴として残す。今回の認識修正と回帰検証は「こんにちは」に限定した。

- 額に2本の指先が届いていても、手首が横向きだと `up > 0.35` で拒否されていた。額に対する指先位置と指の形を確認し、不要な手首の向き条件を削除した。左右反転・左右90度回転の4ケースで修正前の失敗と修正後の通過を確認。
- 額の位置の計算に使わない鼻まで可視性を必須にしていた。最初は両目と両肩で位置を求め、手で隠れる鼻を条件から外した。2・3段階目は胸を基準にするため、現在の両肩だけを必須にする。古い顔座標は流用しない。両目がない最初の段階や、肩がない状態は通過させない。
- 使わない側の手が画面端から切れても全判定が停止していた。片手を使う額の段階では、使える手が1本あれば確認を続ける。両手の段階では、欠けた手を本数に数えて通過させない。
- 一瞬形の判定が外れるだけで保持時間が毎回消えていた。「こんにちは」は1回の不一致を許容するが、不一致を挟む時間は加算しない。2回の不一致、または隣接区間を含め500msを超える不確かさで保持をやり直す。5/10/15/30Hzを検証。手・体の消失や古い映像は引き続き即座に保持時間を消去する。
- 最初の案内を、指の形・額との位置・保持中に分けた。判定できない条件が分かるようにした。
- `hello-step-1.png`〜`hello-step-3.png` を表示。額中央の2指 → 両手の人差し指 → 指のおじぎの3枚。手順選択・再生・カメラの進行と同じ状態に連動し、3段階目の準備に戻った際は2枚目を表示する。制作プロンプトは [hello-image-prompts.md](hello-image-prompts.md)。

全166テスト、型検査、合成入力によるブラウザ19項目、実MediaPipeによる公式静止画像・空画像10ケースを確認。これらは失敗条件と実装の確認であり、利用者の実カメラでの正答率・誤成功率を測定したものではない。

## 対象

選んだ「こんにちは・こんばんは・ありがとう」の指定された手の動きを、PCカメラで順に確認する。自由な手話の認識・翻訳や、表情・文法を含む日本手話全体の評価ではない。数字の旧教材は削除した。

## 教材の根拠

- [秋田市「手話を覚えよう！」](https://www.city.akita.lg.jp/kurashi/shogaifukushi/1006373/1004961.html): 基本教材。こんにちはは額の2指から「あいさつ」、こんばんはは両手の交差から「あいさつ」、ありがとうは手の甲に当てた手を上げる。共通の「あいさつ」は両手の人差し指を近づけて曲げ、会釈する。資料は秋田県聴力障害者協会提供。左右どちらの手でもよいと説明されている。
- [奈良市「あいさつ編」](https://www.city.nara.lg.jp/soshiki/34/77111.html): ありがとうの直角の向き・小指側・会釈を照合。こんにちは・こんばんはの後半の表現には別の形があるため、このアプリの教え方に混在させない。
- [柏崎市「簡単な手話をやってみよう！」](https://www.city.kashiwazaki.lg.jp/soshikiichiran/fukushihokembu/fukushika/3/2/7/45170.html): ろうあ者福祉協会協力の動画。手話表現の地域・年代差が示されている。

公式の写真・動画は転載しない。独自の模式図を使い、原典へのリンクを示す。模式図だけで表現の正確さを保証しない。

## モデルの根拠

- [Google Hand Landmarker Web guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js): 手の21点とworld coordinatesを取得。左右判定スコアは手話の正しさを示す確率ではない。
- [Google Pose Landmarker Web guide](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js): 同じ画像から体の33点とvisibilityを取得。同期推論をWorkerに分け、画面操作を止めない。
- [Pose Landmarker models](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/index): Liteの固定バージョン1を使用。
- [Google公式の姿勢テスト](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/python/test/vision/pose_landmarker_test.py)と[手のテスト](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/python/test/vision/hand_landmarker_test.py): 実モデル起動確認の入力画像を選ぶために参照。

MediaPipeは手話分類器としては使っていない。骨格からこの3課題専用の幾何・時系列ルールを実行する。画像を汎用言語モデルへ送って正誤判定する方式は採用していない。

## 入力と品質条件

同じフレームをHand LandmarkerとPose Landmarkerに通す。手は最大2つ、体は1人。入力画像は非反転で、表示だけを鏡表示する。モデルの左右ラベルはGoogleの実画像と反転画像で確認しており、旧APIの左右入れ替え規則を流用しない。

モデル検出・presence・trackingしきい値は手0.5（Google公式の標準値）、体0.65。以前の手0.7は小さな手や2本目を落とす要因になり得るため変更した。ただし、公式画像で0.7と0.5を比較した範囲では検出数に差はなく、この変更だけで利用者の症状が解消したとの証拠はない。顔（鼻・両目）と両肩のvisibilityは0.6以上で、画面内にあることを要求。肩幅が小さすぎる・大きすぎる場合も受け入れない。これらの値は正答率ではない。

体モデルを2人に設定した初回検証では、映像が切り替わる際に同じ人物の重複トラックが残った。1人用の練習として1トラックに限定した。複数人が映る場面での人物分離は保証しない。

手の座標は全21点が有限、画面内、手のひらの長さが画面高の2.5〜40%という条件を満たす。体を基準にした座標で大きな手の飛び・体位置やスケールの急変を検出したら、今の動きを判定する履歴だけを破棄する。完了した段階は残す。体の位置は毎フレーム更新し、古い顔位置を使い回さない。

## 両手の検出と追跡

`numHands: 2` は以前から設定されていた。公式の `right_hands.jpg` を片手画像の直後に入れると、1フレーム目は1本、次のフレームから2本になることを再現した。Googleの公式テストはこの画像で2本を期待している。これは2本の右手を写したテスト画像なので、どちらも `Right` という結果になる。左右ラベルが同じという理由で2つの手を拒否する従来の処理は不適切だった。

左右分類を一意なIDとして扱う処理を削除し、手首・付け根の位置、短い速度予測、左右分類の補助項で2トラックを対応付ける。左右分類が同じでも位置が異なる2つの手を保持し、出力順が入れ替わってもIDを保つ。ほぼ同じ手首・中心座標の重複だけを取り除く。短い欠落用の内部トラックは最大1秒残すが、観測されない手を表示・判定へ補完しない。交差・強い遮蔽でIDを完全に保証するものではない。

画面の「手をN本検出」は現在の実検出数で、手話の正しさではない。必要本数と顔・肩の状態を別表示し、骨格を2色で描く。安定した手の形・位置・順序が揃わなければ2本映っていても進まない。WorkerのURLに版を付け、古い検出設定のキャッシュを避ける。

## 特徴と状態遷移

3D関節角度と指の長さの比から伸展・屈曲を判定する。人差し指のおじぎではPIP/DIPだけでなくMCPでの屈曲も見る。手の法線を左右に合わせ、手のひらの向きを比較する。

練習を進めやすくするため、指の伸展スコアは0.55以上、畳んだ指は0.7未満まで許容する。伸ばした指の軽い曲がりや、残りの指の緩い握りを受け入れ、親指の畳み方は条件にしない。人差し指を立てる向きにも余裕を持たせる。伸展・屈曲の許容範囲が重なるため、おじぎには確定した開始形から伸展スコアが0.16以上下がるか、付け根に対する向きの値が0.18以上下がる変化も必要とする。曲げた指を静止させたままでは完了しない。必要な指を計測できない場合は引き続き通過させない。これらは実映像の認識率から校正した値ではなく、合成骨格で緩い形・浅いおじぎ・静止形と小さな揺れの区別を確認した練習用の許容値。

画像の座標はピクセルで縦横比を補正してから、両肩の中点を原点、肩幅を単位に正規化する。額は目の中央から肩幅の0.17だけ上を目安にする。個人差を含む概算であり、額への実接触までは判断できない。

| 課題       | 状態遷移と必要な特徴                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| こんにちは | 人差し指・中指を伸ばし、薬指・小指を緩くたたんで指先を額付近へ → 両手の人差し指を胸の前に立てる → 両方の指を曲げる |
| こんばんは | 顔の左右で両手を開き、手のひらをカメラへ → 左右の相対順序が入れ替わるまで交差 → 両手の人差し指を立てて曲げる       |
| ありがとう | 片手の甲を上にして水平に構え、もう片方の開いた手を小指側から近づける → 下の手を保ったまま上の手を上げる            |

静止した最終形だけでは成功しない。形を確定するまで320msかつ3フレーム以上、交差は180ms、最終動作は240msかつ3フレーム以上を見る。表示も同じ状態機械から作り、確定したそのフレームで次の段階・お手本へ進める。「ありがとう」も片手を構える・もう片方をのせる・上げるの3段階を別々に確定する。

完了した段階 `completedSteps` と、今の動きの内部状態 `phase` を分けて管理する。完了数は同じ練習中に減らない。必要な手や顔が消えたら保持時間をゼロにし、再検出後は新たに安定した形を確かめる。消失1秒以上、1秒以上のフレーム間隔、時刻の逆転・重複、体や手の急な移動、追跡IDの変更では、現在動作の開始位置と追跡履歴を捨てて再取得する。30秒の時間制限は削除した。こんにちは・ありがとうの2段階目で手を入れ直しても、1段階目は保持する。

動的な段階の途中で追跡を失った場合は `preparing` として、その段階の始点を案内する。こんばんはの段階2では顔の左右に両手を開く、こんにちはの段階3では両指を立てる、ありがとうの段階3では上の手をのせる形を確認し直す。見出しは「ステップ3の準備」などとなり、段階番号とチェックは戻さない。始点を確認できるまで、終点だけを映しても通過させない。

カメラ停止・認識エラー・タブ非表示でも完了済み段階を残し、「ここから再開」と再開ボタンを示す。停止によるリソース解放と学習のリセットは別の処理。同じことばの選び直しでは変わらず、別のことばへの変更・「最初から」・「もう一度」で明示的に戻る。ページの再読み込み後には保存しない。細いバーは現在の形を保つ時間であり、正答確率ではない。

## CRO-MAGNONの実装を参考にした改善

2026-10-18、ユーザー指定のローカルリポジトリ `CRO-MAGNON` を読み取りで調査した。履歴の設計書には旧仕様が残るため、現行の `src/motion-worker.ts`、`motion-camera.ts`、`motion-hands.ts`、`motion-input.ts` を優先した。元のリポジトリは変更していない。

- `motion-worker.ts`: 同一のHand Landmarker float16 v1モデル・CPU・最大2本・3しきい値0.5だった。モデルを交換すれば片手問題が解決する、という違いはなかった。
- `motion-camera.ts` / `motion-input.ts`: 取得時刻に基づく結果の期限、処理中1フレーム制限、結果受信直後の入力適用、停止と復帰を参考にした。このアプリでは手と体の2モデルを使うため、取得から500ms未満の結果を採用し、100ms周期の監視でも古い表示を消す。CRO-MAGNONの230msをそのまま流用していない。500msは実利用者で最適化した値ではない。
- `motion-hands.ts`: 指の「不明」を「曲げた」に数えない考え方を採用。3D関節が重なり角度を計測できない場合は `null` とし、必要な指の伸展・屈曲やおじぎを成立させない。判別可能な別の指の値は保持する。

手話では額や胸に対する位置と両手の順序を要するため、体の基準、3D指角度、位置による2つの追跡IDを維持した。ゲームの片手モード、枠外での移動継続、同じ左右ラベルを重複として拒否する処理は採用しない。検出しきい値や撮影解像度は今回変更していない。

実ブラウザの検査で、Canvasの映像供給を止めても `video.currentTime` だけが進み、同じ画像が新しい入力として繰り返されることを再現した。このアプリでは [requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback) と [getVideoPlaybackQuality](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/getVideoPlaybackQuality) のフレーム数を使う。表示コールバックが間引かれても、監視側で取得済みフレーム数を確認する。時刻だけを映像の生存証拠にしない。

処理中の取得時刻と一致しない応答・重複応答は捨てる。新しい結果が500ms届かないと骨格を消し「認識を待っています」と表示する。停止中は保持時間を加算しない。1秒以上の入力間隔では現在動作の開始形を確認し直すが、完了段階は残る。8秒の映像停止または処理無応答でWorkerとカメラを解放する。再開時も完了段階は維持する。ライブカメラの誤成功率を測った結果ではなく、停止・遅延時の誤動作を防ぐ変更。

## 実測で確認できたこと

- 75件の合成骨格テストで、動作順序、左右反転、相対位置、追跡ID、各段階の表示、短い・長い欠落、不正値・遅延結果・計測不能な指の拒否、10/15/30Hzでの順序判定、45秒の試行、手を置き直す場合の同じ段階での再試行を確認。
- ブラウザの遅延・復帰14項目で、650ms遅れた結果を不採用、短い停止後の自動復帰、骨格の消去、重複応答、映像停止とWorker無応答からの資源解放、停止後の完了段階の保持を確認。
- 途中再開のブラウザ21項目で、2秒超の検出切れや間違った形でもチェックが消えず、停止・再開後に次の段階へ進めること、動きの始点を確かめ直す案内、明示的リセットを確認。
- 公式画像4種と空画像、それぞれの反転を含む10ケースで、実モデルが動作し、静止画像をあいさつの完成として通さないことを確認。
- ブラウザではカメラ処理・状態遷移・表示・停止を確認。成功フローでは決定的な合成骨格を入力した。
- 両手の公式写真、その反転、大中小の左右2本を配置した画像、片手→両手→片手→両手、空画像の9ケースを各7フレーム入力し、最後の3フレームで期待する本数を検出。2本を再検出するまで1〜2フレームかかったケースもある。
- 公式の両手写真をcanvasの模擬カメラ映像に流し、実Worker・実モデルを通った「手を2本検出」と2色の骨格表示を確認。利用者の実カメラ・実手話の再現テストではない。

**これらは実際のあいさつ動画の認識率を示さない。** Precision、Recall、誤成功率は未測定。実映像で3つの正しい動作すべてを認識できたとの主張はしない。

## 残る限界・次の精度評価

手の重なり、横向きの手、動体ぶれ、逆光、体形、指の可動域、衣服、機器、カメラ距離で失敗する可能性がある。左右分類の揺れや、肩・目の推定のずれによる誤判定もある。深度接触、表情、口形、頭の会釈を正誤判定しない。顔や体の点を使うのは位置の基準だけ。

ろう者・手話講師に教材と模式図を確認してもらい、同意を得た複数の利用者・照明・左右・距離で収録した動作を評価する。収録時は同じ人の映像を学習用と評価用に分けず、利用者を分離する。正しい動き、順番違い、片手だけ、日常動作、無動作を混ぜて、語彙別のPrecision/Recallと誤成功回数・やり直し回数・遅延を測る。しきい値を調整したあと、未使用の評価映像で再測定する。必要なら同意・権利処理済みの時系列データで専用分類器に置き換える。
